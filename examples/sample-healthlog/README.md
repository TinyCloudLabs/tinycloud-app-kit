# Health Log (sample tiny app)

`xyz.tinycloud.sample.healthlog`: an app-type artifact (PLAN-TINYAPPS T2). Meals + weight, a today card, a
last-7-days chart. Written from scratch from TinyCloud's public specs (the manifest schema and OKF v0.2 in this kit); it contains no
third-party app code. It is original work, so its manifest carries no `forked_from` (the kit schema reserves that
for copies).

## The artifact (what ships; listed with sha256 in `release.json`)

| File | What |
|---|---|
| `manifest.json` | `app_id`, grants (SQL `healthlog` read/write/schema; KV `prefs/` get/put, `app/` get, `knowledge/` get/put/list: only what the app calls, plus the knowledge prefix agents use), `knowledge: "knowledge/index.md"` |
| `schema.sql` | tables `meal`, `weight`; views `day_card`, `week_rollup`. Comments beside columns become the knowledge descriptions |
| `app.jsx` | React + recharts + Tailwind classes; imports only `react`, `recharts`, `@tinycloud/app` |
| `knowledge/` | OKF v0.2 bundle **generated by this kit's `scripts/okf.mjs`**: `index.md`, `app.md`, `tables/`, `views/`, `kv/`, `log.md` |
| `release.json` | `{schema, app_id, version, files:[{path,sha256,size}], digest}`; `digest` = sha256 of sorted `"<path> <sha256>"` lines |

Not shipped: `dev/` (shim, dev server), `tests/`, `scripts/`, `knowledge-src/` (hand-written source for `app.md`).

Write protocol (app and `knowledge/app.md` agree): client-generated `op_id` (UNIQUE) per entry,
`INSERT ... ON CONFLICT(op_id) DO NOTHING`, then always read the row back by `op_id`. Retries (only for
TIMEOUT/BUSY/INTERNAL, once) reuse the same `op_id`. The forms hold one `op_id` per submission and a ref guard stops
double submits.

## Bridge API assumed (`import { sql, kv } from "@tinycloud/app"`)

Contract is in the header of `dev/shim.mjs` (the T3 builder reuses it). Nothing throws; every call resolves to
`{ok:true,...}` or `{ok:false,error:{code,message}}`.

```
kv.get(key)                         -> {ok, bytes: Uint8Array, contentType?}
kv.put(key, body, {contentType?, ifNoneMatch?: true}) -> {ok}     body: string | Uint8Array
kv.list(prefix = "")                -> {ok, keys: string[], truncated}   keys relative to <app_id>/
kv.del(key)                         -> {ok}
sql.query(db, text, params = [])    -> {ok, columns, rows: any[][], rowCount}   read statements only
sql.execute(db, text, params = [])  -> {ok, changes, lastInsertRowId}           write/schema statements
```

`key`/`db` are relative to `<app_id>/` ("prefs/goals.json", "healthlog"); a leading `/` means an absolute path in
the space (only reachable via a `skipPrefix` grant). Error codes: `PERMISSION_DENIED NOT_FOUND PRECONDITION_FAILED
SQL_ERROR BAD_REQUEST TOO_LARGE BUSY TIMEOUT INTERNAL NOT_CONNECTED`. Caps: 1 MB per call, 4 in flight (the 5th is
refused with `BUSY`, not queued), 30 s (`TIMEOUT`: the call may have been applied, so read back before retrying).
The shim checks `(service, path, action)` against the app's own resolved manifest before calling the node, as the
T5b parent will; the node remains the backstop (tested). `app.jsx` keeps itself at 3 concurrent calls.

**SQL statement classes (T5b: the real bridge MUST implement this).** tinycloud-node enforces SQL by the ability a
delegation carries, not by which call was used: on v1.20.6 and v1.21.0 a `DROP TABLE` sent as a *query* executes when
the delegation has `schema`. So the bridge classifies every statement itself (`classifySql` in `dev/shim.mjs`, with
tests in `tests/shim.test.mjs`) and refuses what it cannot classify: `sql.query` takes exactly one read statement
(`SELECT`, `VALUES`, a read-only `WITH`, `EXPLAIN` of a read); `sql.execute` takes exactly one write or schema
statement. Refused everywhere: more than one statement, `PRAGMA`, `ATTACH`, `DETACH`, `VACUUM`, `load_extension`,
transactions, anything unterminated or unknown. Comments and literals are blanked before looking, so keywords inside
them neither hide nor trigger anything. The class then picks the ability checked against the manifest.

The shim never throws: bad `opts` (circular, wrong types, unknown keys, throwing getters) and other malformed
arguments give `BAD_REQUEST`; `null` options mean `{}`.

## Run it

From a clean clone of the kit:

```
cd examples/sample-healthlog
npm ci
npm test
```

`npm test` runs three files with `node --test`. `bundle.test.mjs` and the today-card test need nothing else. The
suites that talk to a real node are **skipped with a message, not failed**, unless `TC_NODE_BIN` points at a prebuilt
`tinycloud` binary (a tinycloud-node release build; no Docker, no source build needed):

```
TC_NODE_BIN=/path/to/tinycloud npm test
```

Each test file starts its own throwaway node on a free port with a temp data dir and deletes it afterwards. Stop only
processes you started yourself.

```
npm run knowledge          # regenerate knowledge/ with ../../scripts/okf.mjs from manifest.json + schema.sql + knowledge-src/
npm run knowledge:check    # okf.mjs check knowledge --manifest manifest.json (the kit's `npm run okf:check` covers it too)
npm run release            # rewrite release.json (sha256 of every shipped file)
TC_NODE_BIN=/path/to/tinycloud npm run dev    # real browser on http://127.0.0.1:5173/ (throwaway node, seeded data)
```

## The dev bridge (`dev/shim.mjs`) is temporary

`import { sql, kv } from "@tinycloud/app"` is the bridge the app runs against inside the tiny-app runner. That real
bridge (postMessage to the parent page) is not part of this kit: it is built separately in the share repo. Until it
exists, `dev/shim.mjs` implements the same contract on top of `@tinycloud/node-sdk` so the app and its tests run against
a real node. It also plays the parent's part: a per-call check against the app's own manifest, size / in-flight /
timeout caps. It is not shipped with the app (see `release.json`).

## Test coverage

With `TC_NODE_BIN` set: 56 tests, all passing. Without it: the 26 node-backed tests are reported as skipped suites and
the other 30 pass.

- `tests/healthlog.test.mjs` (21, node): provision the schema from the installed `app/schema.sql`; shim-driven app logic
  logs a meal + weight and `day_card` shows them; latest weight of the day; `week_rollup` gap-fill and 7-day averages;
  op-id replay gives one row; a lost response (applied) and a dropped call (not applied) both end with exactly one row;
  schema CHECKs reject bad rows; target validation and fallback; manifest enforcement in the shim and by the node itself
  when the shim check is bypassed; `null` put options; caps.
- `tests/shim.test.mjs` (13, no node): `classifySql` (read / write / schema / refused, including multi-statement,
  `WITH ... INSERT`, `load_extension`, `PRAGMA`, `ATTACH`, `VACUUM`, comment- and literal-hidden text); the shim refuses
  those before the node client is reached (a stand-in client that fails the test if touched); circular or odd arguments
  never throw; `del`/`list` on `prefs/` and `list` on `app/` are denied by the manifest.
- `tests/render.test.mjs` (13, jsdom; 8 need no node): today card from a `day_card` row and for an empty day; the daily
  target: an invalid value (`abc`, `0`, `2300.5`, ...) shows an `role="alert"` message, restores the previous value and
  stores nothing; a failed save does the same; a stored target of 0 cannot make a `NaN%` bar; the chart draws all seven
  weekday labels, a legend, and an accessible per-day summary; whole app through the shim (node): first open
  provisions, double submit writes one row, rejected input keeps the form, weight updates the card.
- `tests/bundle.test.mjs` (9, no node): manifest valid and grants exact; `release.json` fresh with correct sha256;
  `okf.mjs check knowledge --manifest manifest.json` passes; regenerating over `knowledge/` changes nothing; layout and
  `resource:` form; the static scan of `app.jsx` (below).

**The static scan is defence in depth only.** `tests/lib/scan.mjs` is a source-text deny-list plus a few patterns (URLs,
`new Image`, `.src =`, bracket access on globals, extra imports ...). A determined author can write code it does not
recognise. The real boundary is the runner's sandbox (opaque origin, a CSP with `connect-src 'none'`, no storage, no
parent access), proven in T5b, not here. The scan catches honest mistakes early and has its own tests, including
indirect forms like `globalThis["fe"+"tch"]` and `new Image().src = url`.

## Taking screenshots

Run `TC_NODE_BIN=/path/to/tinycloud npm run dev` (throwaway node, seeded data, `http://127.0.0.1:5173/`; stop it with
Ctrl-C). Then drive any Chromium: for example puppeteer with `page.setViewport({ width: 390, height: 900 })` and
`page.screenshot({ fullPage: true })`, plus `page.emulateMediaFeatures([{ name: "prefers-color-scheme", value: "dark" }])`
for dark mode. Plain `chrome --headless --window-size=390,...` enforces a minimum window width and can crop the
right edge, which looks like a layout bug but is not: check `document.documentElement.scrollWidth` against
`clientWidth` instead (both are 390 here). The dev server's `/bridge` endpoint is bound to 127.0.0.1, answers only
for its own Host/Origin, and needs a per-run random token that only the served page receives. No screenshots are
committed.

## Limits (honest)

- The shim is a stand-in: no iframe, no postMessage, no sandbox CSP. The sandbox rules on `app.jsx` are only
  checked statically (above); T5b is where the sandbox itself gets proven.
- Label dropping at phone width needs real layout, so jsdom cannot show it; it was checked in headless Chrome at 390 px
  (all seven weekday labels drawn, light and dark).
- Photos/thumbnails and any in-app AI are out of scope for this sample.
