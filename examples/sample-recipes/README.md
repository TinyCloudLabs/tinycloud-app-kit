# Recipes (sample tiny app)

`xyz.tinycloud.sample.recipes`: an app-type artifact (PLAN-TINYAPPS T3). Shelves, a recipe list and detail view,
add/edit recipe, and "from a health-log entry", which reads the Health Log sample's `meal` table through a
**read-only cross-app grant**. Written from scratch (own schema, own code); `forked_from` is `null`.

## The artifact (what ships; listed with sha256 in `release.json`)

| File | What |
|---|---|
| `manifest.json` | `app_id`, own grants (SQL `recipes` read/write/schema; KV `prefs/` get/put/del/list, `app/` get/list, `knowledge/` get/put/list), **read-only** grants on `xyz.tinycloud.sample.healthlog` (SQL `healthlog` read; KV `knowledge/` get/list, both `skipPrefix`), `knowledge: "knowledge/index.md"`, `forked_from: null` |
| `schema.sql` | tables `recipe`, `shelf`, `recipe_shelf`, `meal_link`; views `recipe_card`, `shelf_overview`. Comments beside columns become the knowledge descriptions |
| `app.jsx` | React + Tailwind classes; imports only `react` and `@tinycloud/app` |
| `knowledge/` | OKF v0.2 bundle **generated by the kit's `scripts/okf.mjs`**: `index.md`, `app.md`, `tables/`, `views/`, `kv/`, `log.md` (4 tables, 2 views, 4 KV prefixes) |
| `release.json` | `{schema, app_id, version, forked_from, files:[{path,sha256,size}], digest}` (same shape as the Health Log sample) |

Not shipped: `dev/` (the bridge shim), `tests/`, `scripts/`, `knowledge-src/` (hand-written source for `app.md`).

## Schema in one paragraph

`recipe` holds the recipe (ingredients and steps as JSON text, optional per-serving nutrition plus `nutrition_basis`,
`origin` own/adapted/from_meal). `shelf` names a group; `recipe_shelf` is the many-to-many join. `meal_link` records
that a recipe was started from Health Log meal `health_meal_id`, with a snapshot of the meal's day, name and kcal so
the list renders without reading the other app. The link lives in this app's database; nothing is ever written to
the Health Log. Ids are client-generated text (`rcp_`, `shf_`, `lnk_`). Foreign keys are declared but not enforced by
the node, so the app deletes child rows first.

## Cross-app permission model

The manifest asks for `tinycloud.sql` `read` on `xyz.tinycloud.sample.healthlog/healthlog` and `get, list` on
`xyz.tinycloud.sample.healthlog/knowledge/`. Both are `skipPrefix` grants, reached through the bridge with a leading
`/` (`sql.query("/xyz.tinycloud.sample.healthlog/healthlog", ...)`). Tested on a real node
(`tests/cross-app.test.mjs`): reads work; INSERT/UPDATE/DELETE/DDL and every KV write or delete under the Health Log's
prefix are refused, both by the bridge (`PERMISSION_DENIED`) and, with the call forced past the bridge, by the node
itself (`AUTH_UNAUTHORIZED`).

Two facts found on the way, relevant to T5b:

- The node authorizes a SQL statement by its class (`read` / `write` / `schema`), so the app's session must carry
  exactly the manifest's ReCap. A **wallet-mode** `TinyCloudNode` escalates its own session on demand and would let
  the write through, so the tests give each app a signer-less client (`restoreSession` from a manifest-scoped
  session), which is what the runner will hold.
- A KV key outside every grant is refused by the node for reads and writes alike; a SQL database outside every grant
  fails with `AUTH_UNAUTHORIZED` too.

## Bridge API assumed

Identical to the Health Log sample: `dev/shim.mjs` is a byte-for-byte copy of that sample's shim, whose header is the
contract (`kv.get/put/list/del`, `sql.query/execute`; nothing throws; `{ok:true,...}|{ok:false,error:{code,message}}`;
paths relative to `<app_id>/`, leading `/` = absolute; caps 1 MB / 4 in flight / 30 s). The app keeps itself to 3
concurrent calls (asserted in `tests/render.test.mjs`) and serializes its own `prefs/ui.json` writes, because the
bridge does not order concurrent calls.

Storage-full behavior follows the kit guide: schema setup reads first and writes only if something is missing, a
storage rejection shows a persistent read-only banner and never raw node text, and a partly saved recipe says which
part was saved.

## Run it

```
npm install
export TC_NODE_BIN=/path/to/tinycloud-node       # a native node binary; without it the node-backed tests SKIP with a message
export TC_APP_KIT=/path/to/tinycloud-app-kit     # optional: found automatically when this app sits in the kit's examples/
npm test
npm run knowledge          # regenerate knowledge/ (keeps <!-- keep --> blocks)
npm run knowledge:check    # okf.mjs check knowledge --manifest manifest.json
npm run release            # rewrite release.json
```

Each node-backed test file starts one throwaway native node on a free port with a temp data dir and stops exactly the
process it started (no pattern kills). No Docker. `node_modules/` is not committed.

## Tests

- `tests/bundle.test.mjs`: manifest valid and its grants exact, anything outside the app's own prefix is read-only;
  `release.json` fresh with correct sha256; knowledge coverage (a concept per table, view and KV prefix; `resource:`
  form); `okf.mjs check` passes; regenerating changes nothing; `app.jsx` imports only react and the bridge and has no
  network/eval/storage/postMessage/innerHTML use.
- `tests/recipes.test.mjs`: Health Log rows written through that app's own session, then a recipe created from a
  meal id and read back; shelves, search, favorites, delete cascade; form validation; CHECK sets enforced by the node.
- `tests/cross-app.test.mjs`: the read-allowed / write-refused proof above.
- `tests/render.test.mjs`: jsdom render of the recipe list and the flows around it, against a real node.

`tests/fixtures/healthlog/` holds copies of the Health Log sample's manifest (named `healthlog.app.json` so the kit lint does not scan it) and schema, used only to stand up the other
app's data. Re-copy them when that sample changes.
