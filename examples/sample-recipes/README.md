# Recipes (sample tiny app)

`xyz.tinycloud.sample.recipes`: an app-type artifact. Shelves, a recipe list and detail view, add/edit recipe, and
"from a health-log entry", which reads meals from the [Health Log sample](../sample-healthlog/) through a
**read-only cross-app grant** on that app's whole `healthlog` database (SQL grants are per database, not per table, so
body-weight entries and the daily summary views are readable too; the app only ever queries `meal`, and a test asserts it). Written from scratch from TinyCloud's public specs; it contains no third-party app code.
It is an original app, so its manifest has no `forked_from`.

## The artifact (what ships; listed with sha256 in `release.json`)

| File | What |
|---|---|
| `manifest.json` | `app_id`, own grants (SQL `recipes` read/write/schema; KV `prefs/` get/put, `app/` get, `knowledge/` get/put/list; every grant is one the app calls, except `knowledge/`, which is the app's own bundle per the interop spec), one **read-only** grant on `xyz.tinycloud.sample.healthlog` (SQL `healthlog` read, `skipPrefix`), `knowledge: "knowledge/index.md"` |
| `schema.sql` | tables `recipe`, `shelf`, `recipe_shelf`, `meal_link`; views `recipe_card`, `shelf_overview`. Comments beside columns become the knowledge descriptions |
| `app.jsx` | React + Tailwind classes (light and dark); imports only `react` and `@tinycloud/app` |
| `knowledge/` | OKF v0.2 bundle **generated by the kit's `scripts/okf.mjs`**: `index.md`, `app.md`, `tables/`, `views/`, `kv/`, `log.md` (4 tables, 2 views, 3 KV prefixes) |
| `release.json` | `{schema, app_id, version, files:[{path,sha256,size}], digest}` (same shape as the Health Log sample) |

Not shipped: `dev/` (build helper and dev server), `tests/`, `scripts/`, `knowledge-src/` (hand-written source for `app.md`).

## Schema in one paragraph

`recipe` holds the recipe (ingredients and steps as JSON text, optional per-serving nutrition plus `nutrition_basis`,
`origin` own/adapted/from_meal). `shelf` names a group; `recipe_shelf` is the many-to-many join. `meal_link` records
that a recipe was started from Health Log meal `health_meal_id`, with a snapshot of the meal's day, name and kcal so
the list renders without reading the other app. The link lives in this app's database; nothing is ever written to
the Health Log. Ids are client-generated text (`rcp_`, `shf_`, `lnk_`). Foreign keys are declared but not enforced by
the node, so the app deletes child rows first.

## Cross-app permission model

The manifest asks for `tinycloud.sql` `read` on `xyz.tinycloud.sample.healthlog/healthlog`, a `skipPrefix` grant reached
through the bridge with a leading `/` (`sql.query("/xyz.tinycloud.sample.healthlog/healthlog", ...)`). That is the **whole
database**: `meal`, `weight`, `day_card` and `week_rollup` are all readable by this app, and the manifest description and
`knowledge/app.md` say so. The app itself only queries `meal`. It asks for no KV
access to the Health Log (it never calls it), and the tests show that is refused too. Tested on a real node
(`tests/cross-app.test.mjs`): reads work; INSERT/UPDATE/DELETE/DDL and every KV read, write or delete under the Health Log's
prefix are refused, both by the bridge (`PERMISSION_DENIED`) and, with the call forced past the bridge, by the node
itself (`AUTH_UNAUTHORIZED`). A KV key or SQL database outside every grant is refused by the node for reads too.

## For the runner (requirement found while testing, for T5b)

**The runner MUST hold a manifest-scoped session restored without a signer, and its tests must prove that the forbidden
write is refused.** A wallet-mode `TinyCloudNode` (one built with a `privateKey`) escalates its own session on demand:
given a manifest that grants only `read` on another app's database, it still let an `INSERT` through (observed; the SDK escalates a wallet client's session on demand, which I did not trace
further). A client built with `new TinyCloudNode({ host })` and `restoreSession(<session from the manifest-scoped
sign-in>)` holds exactly the manifest's ReCap and nothing else, and the node refuses the same write. These tests do that
(`tests/lib/stack.mjs`, `appSession()`), and the cross-app test fails if a write the manifest does not grant ever succeeds.
The parent-side manifest check in the bridge is a first line; the node is the backstop, and the node only is one if the
session cannot sign for more.

## Bridge API assumed

The same bridge as the Health Log sample, and the same file: tests and the dev server use
`../sample-healthlog/dev/shim.mjs` (one source of truth, no copy; its header is the contract) (`kv.get/put/list/del`, `sql.query/execute`; nothing throws; `{ok:true,...}|{ok:false,error:{code,message}}`;
paths relative to `<app_id>/`, leading `/` = absolute; caps 1 MB / 4 in flight / 30 s; `sql.query` takes one read-only
statement, refusing multiple statements, `WITH ... INSERT`, PRAGMA, ATTACH, VACUUM and `load_extension`). The app keeps itself to 3
concurrent calls (asserted in `tests/render.test.mjs`) and serializes its own `prefs/ui.json` writes, because the
bridge does not order concurrent calls.

Storage-full behavior follows the kit guide: schema setup reads first and writes only if something is missing, a
storage rejection shows a persistent read-only banner and never raw node text, and a partly saved recipe says which
part was saved.

## Run it (from a clean clone of the kit)

```
cd examples/sample-recipes
npm run setup                                      # npm install here AND in ../sample-healthlog (it owns the shared bridge shim)
npm test                                           # no node binary: the node-backed files SKIP with a message; the bundle checks still run
TC_NODE_BIN=/path/to/tinycloud-node npm test       # a native tinycloud-node binary: runs everything (59 tests; without it 15 run and 3 suites skip)
npm run knowledge                                  # regenerate knowledge/ (keeps <!-- keep --> blocks), uses ../../scripts/okf.mjs
npm run knowledge:check                            # okf.mjs check knowledge --manifest manifest.json
npm run release                                    # rewrite release.json
TC_NODE_BIN=... npm run dev                        # real browser on seeded data: http://127.0.0.1:5174/ (?theme=dark for dark)
                                                   # binds 127.0.0.1; /bridge needs a per-run token and own Host/Origin; refuses to start if the port
                                                   # is taken, and stops the node it started on exit, signals and failures
```

Each node-backed test file starts one throwaway native node on a free port with a temp data dir and stops exactly the
process it started (no pattern kills). No Docker. `node_modules/` is not committed. The tests read the Health Log
sample's manifest and schema from `../sample-healthlog/`, so this example follows that sample's schema.

## Tests

- `tests/bundle.test.mjs`: manifest valid, no `forked_from`, grants exact, anything outside the app's own prefix is
  read-only; `release.json` fresh with correct sha256; knowledge coverage (a concept per table, view and KV prefix;
  `resource:` form); `okf.mjs check` passes; regenerating changes nothing; `app.jsx` imports only react and the bridge
  and passes the Health Log sample's static scan (`../sample-healthlog/tests/lib/scan.mjs`; defence in depth, the sandbox
  CSP is the boundary).
- `tests/classify.test.mjs` (no node needed): a recording stand-in for the node client shows every statement the app
  sends (the `recipe_card` / `shelf_overview` reads, the cross-app `meal` read, all writes) passes the shim's SQL
  class check in the right class, that every cross-app statement touches only `meal`, and that writes toward the Health Log never leave the shim.
- `tests/recipes.test.mjs`: Health Log rows written through that app's own session, then a recipe created from a
  meal id and read back; shelves, search, favorites, delete cascade; form validation including upper bounds (servings 1000, minutes 10080, calories 5000, macros 10000 g), with the same bounds enforced by the node.
- `tests/cross-app.test.mjs`: the read-allowed / write-refused proof above.
- `tests/render.test.mjs`: jsdom render of the recipe list and the flows around it, against a real node; malformed or out-of-range numbers show an alert and write nothing; long unbroken text can wrap.

## Looking at it

`npm run dev` (see above) serves the app on seeded data (a few meals in the Health Log sample and four recipes); add `--long`
for one recipe and one shelf with very long unbroken text. `?theme=dark` forces dark. The screens (list, detail, edit,
meal picker, shelves) were checked in headless Chrome at 390 and 1440 px, light and dark, and the page never scrolls
sideways (`scrollWidth` equals the viewport, including with `--long`). No screenshots are committed.

## Limits

- The shim is a stand-in: no iframe, no postMessage, no sandbox CSP. The `app.jsx` sandbox rules are checked
  statically (`bundle.test.mjs`), not by the S3 sandbox; T5b is where that gets proven.
- Photos, units conversion and any in-app AI are out of scope for this sample.
